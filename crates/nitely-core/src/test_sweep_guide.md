# Test hygiene sweep

Read the project's brief and docs/testing.md first. This is a report and proposal task: do not edit or remove tests, commit, or submit a cleanup before the human has approved its candidate list.

1. Prefer existing evidence: JUnit XML from any runner that writes it (pytest `--junitxml`, the jest and vitest junit reporters, gotestsum, cargo-nextest, .NET, Maven Surefire, Gradle), Rust libtest output, Node TAP, or a CI job log of them (`gh run view --log`). A file read only in part (cut, malformed, a binary that never finished) is a partial run: what it did not report is unknown, never passing. Record the actual revision and a distinct run identifier for every log. Never assign an old log to the current revision or count one run twice. `nitely test-sweep collect --logs evidence.json --output report.json` inventories tracked test sources and imports logs without running a suite. The evidence file is an array of `{ "path": "absolute log path", "revision": "40-character commit", "run": "distinct run ID", "source": "lane 42" }`. With no logs it produces explicitly static-only evidence.
2. When measurements are missing, `nitely test-sweep measure --out evidence/` gathers them without running a suite on this machine: first the logs and JUnit artifacts of finished CI runs at HEAD (read with `gh`, nothing runs); else it shows the CI run it would dispatch, with its cost cap (`--minutes`, default 30, per run) and `--runs` (default 2: two runs at one revision tell a flaky test from a failing one), and starts it only with `--dispatch`. A dispatch runs the commands whose console says each test's outcome: cargo test and node:test as they are, pytest and `go test` with `-v` added; other runners need CI to upload JUnit as a test artifact. When HEAD has no CI evidence, `measure` reads the logs of the newest main commit CI tested, filed under that commit; collect them with `collect --logs evidence.json --at <that commit>`, which reads that commit's tests from its own tree. A repo with CI never measures on this machine, including a repo set up for another CI (Bitbucket Pipelines, GitLab CI, CircleCI, Azure Pipelines, Jenkins, Travis, Buildkite), which Nitely cannot dispatch to: if `gh` is signed out, or CI has no suite workflow (`[lanes] ci_commands`), `measure` says so and stops. Only a repo without CI (or one this machine keeps local) gets a build-lane run, each command capped, shown the same way and started with `--lane`. Commit everything first, and write `--out` outside the repo when tests run. It writes the logs and `evidence.json` for `collect --logs`. Each observation keeps its method (`ci-log`, `ci-run`, `lane`, `imported`), and times are compared within one method only. `nitely test-sweep collect --execute --runs 2 --seconds 600 --output report.json` (a repo without CI only) runs Rust and Node suites in a build lane, with a bounded budget, and retains per-test outcomes and available timings. Add `--rust-timings` for stable Rust binaries measured one test at a time; this costs more and includes process startup, so compare using the same method. `--known-failures names.json` reads an explicit JSON array of test names/IDs and highlights matching observed failures. Reuse this report on later steps. Do not run another full gate just to make a sweep report. A timeout, missing timing, unsupported reporter, ambiguous test name, or revision mismatch is unknown, never passing.
3. Read the report, compare duplicates in their real fixture/import context, and inspect heavy mocks. Repeated failures need repair or a reasoned retirement decision, not silent deletion. Known-failure lists do not make failures acceptable; name the list and its matching tests in the evidence. To propose a removal, change that candidate's kind to `delete` only after recording the surviving contract/regression test in its evidence. Similarity alone supports only `inspect`.
4. Classify the flagged tests (`nitely test-sweep map report.json`, the classify guide), then `nitely test-sweep propose report.json --classes classes.json --issue APP-42` (MCP: `test_optimize_propose`) creates ONE goal proposal: a refactor card per module with the decisions to lift, the scenarios it keeps and the time measured on its tests; a card for clock waits; the test budget naming the scenarios; one deletion card, blocked by the refactors, naming what covers each test; and, where the repo has CI and it does not run every test command yet, a playbook proposal for `ci_commands`. Pass the current sweep issue as --issue. Do not approve either yourself. The person edits and approves the refactors module by module; the deletion card's agent asks once with its list after they land, and deletes only what the person approves.
5. Record counts, warm execution time where measured, flakes and unknowns in the sweep issue. After approved changes land, record the same before/after measures in docs/testing.md; do not invent improvements without measurement. A report without candidates needs only a handoff noting its coverage and limitations.

`[schedule] test_sweep = "nightly"` (or `weekly`, default `off`) asks a running Crew to create a report-only sweep task once per UTC period. It respects Crew pause/draining and never changes the playbook itself. A pending sweep prevents duplicate jobs. No schedule enables automatic test deletion.
